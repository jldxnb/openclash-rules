## 一、结论与此前判断的更正

已确认的配置值问题是节点排除正则的点号未转义。其他重要发现主要是 DNS/代理相互依赖、私网 IP 缺少显式直连兜底、单一探测站点、Android DNS 绕过、额外监听面及策略组行为风险，发生条件和解决方法见后文。

此前对这份配置的部分判断不准确，不能据此改坏正常配置：

| 此前判断 | 核对后的结论 |
|---|---|
| 负向前瞻 `(?!...)` 必然导致 mihomo 失败 | 当前 mihomo 策略组使用 `github.com/dlclark/regexp2`，不是 Go 标准库 RE2；支持负向前瞻。173-174 行不能仅因使用该语法判为 bug。 |
| 劫持 53、监听 1053 端口不一致是 bug | `tun.dns-hijack` 将连接导入内部 DNS 模块，不要求转发到 `dns.listen` 的端口；这是正常组合。 |
| gstatic 健康检查因为本地不能直连就必然全红 | 节点健康检查通过被测节点执行。订阅下载的 `proxy: DIRECT` 不意味着节点探测走 DIRECT。风险是探测站点在节点线路上不可达，而非仅仅本机直连受限。 |
| `max-failed-times: 1` 表示一次失败马上切换 | 该值用于连接失败后触发健康检查，不是简单的切换次数阈值；最终选择取决于节点健康状态及 fallback 行为。 |
| 不写 `fallback-filter` 就只在 DNS 超时后使用 fallback | 配置 fallback 后有默认过滤规则，官方文档注明默认 `geoip-code: CN`。不能把省略字段理解为没有过滤。 |
| 显式“非港台”“非日本”策略组必然被自己的 filter 删除 | 当前源码对显式 `proxies` 的 compatible provider 跳过 inclusion filter；不能因名称包含禁词就断言显式链被删除。 |
| 不写 provider `path` 就没有缓存 | rule-provider 省略 path 时默认以 URL 的 MD5 命名缓存。问题是缓存是否存在、有效、可用，而不是必然没有缓存。 |

以上更正依据的是当前上游实现；FlClash 实际捆绑核心仍应核对版本。没有证据时，不应要求重写负向前瞻、把监听端口改成 53、改名显式链或删除所有缓存机制。

## 二、外站 IP 异常的排查入口

首先区分两种地址：

- **目标服务器 IP**：应用/DNS 查询得到的网站地址。应检查 DNS 答案、缓存、域名映射、是否绕过内核及服务器可达性。
- **公网出口 IP**：网站显示访问者来自哪里。应检查规则命中、模式、策略组实际选择、节点出口及是否 DIRECT。

CDN 返回地址不同或不同 DNS 返回不同地区地址，不等于答案错误。至少需要域名、实际答案、两种独立解析器的对照、连接错误和实际出站链，才能判断污染或失效。`redir-host` 返回真实 IP 也不等于不能按域名分流：内核仍可用 DNS 映射和嗅探恢复域名。

### 1. 境外 DNS 与代理可用性存在启动依赖

**优先级：P1；性质：配置依赖已确认，是否触发需实机验证。**

**位置：143 行 `respect-rules`；147-153 行节点/直连解析器；158-167 行境外 DNS 和 policy；231、239 行相关域名路由。**

配置启用了 `respect-rules: true`，因此 DNS 上游连接遵守路由规则。`geosite:geolocation-!cn` 使用 Cloudflare/Google DoH，而不是无条件直连。若这些 DoH 的连接经规则进入当前不可用的策略组，境外解析就会失败；Google DoH 的路由还可能与 `google_domain` 指向 AI 组的选择相关，应看连接日志而非猜测。

节点域名有独立 `proxy-server-nameserver`，这已经有助于避免节点解析递归依赖；但其两个国内 DoH 能否正确解析实际节点地址仍需验证。节点地址解析失败、相关链没有合格节点、保存的选择已失效，都可能使境外 DoH 不可用。

**解决方法：**

- 查看 `dns.google`、`dns.cloudflare.com` 的真实规则命中、所选组及节点；核对查询超时是否和组不可用同时出现。
- 如有必要，给 DNS 上游连接指定经过验证的可用出站路径；修改时保留按机场选择的能力，并避免节点解析依赖自身出站。
- 对代理节点域名单独用 `proxy-server-nameserver` 中的解析器验证，必要时采用可靠的专用节点解析源。
- 不要直接关闭 `respect-rules` 作为通用修复：这可能让境外 DoH 改为直连，反而在受限网络失败。

### 2. 应用加密 DNS 不受这两条 53 劫持规则直接处理

**优先级：P1/P2；性质：劫持范围已确认，是否导致故障取决于设备和应用。**

**位置：131-133 行。**

当前劫持 UDP/TCP 53。Android 私人 DNS（DoT）及应用内 DoH 通常使用其他端口，因此不会被这两条规则直接送入内部 DNS 模块。它们仍可能通过 VPN/TUN 代理出站，不能把“未进入 mihomo DNS”直接等同于“泄漏到运营商”或“整个流量绕过 VPN”。风险在于解析答案与内核 DNS policy 不一致、域名映射缺失，以及应用排除/VPN 绕过时走其他路径。

**解决方法：**

- 在同一设备做私人 DNS 开/关、应用安全 DNS 开/关对照，并确认 FlClash 应用排除、VPN 接管范围及连接日志。
- 需要统一解析行为时，先禁用应用自带解析或配置其使用经过验证的路径；不要把普通 443 全部当 DNS 拦截。
- 验证 UDP 53 和 TCP 53 已进入内部 DNS；无需把 `listen: ...:1053` 改成 53。

### 3. redir-host、缓存和域名恢复存在条件性风险

**优先级：P2；性质：模式取舍，不是 redir-host 本身的 bug。**

**位置：99、101-122、142 行。**

真实 DNS 答案可能受污染或 CDN 调度影响。纯 IP 连接、应用自己的解析、共享 IP、多种加密协议等场景下，域名恢复未必完整。配置已启用 DNS mapping 与 sniffer，不能声称 redir-host 一定丢失域名；`store-fake-ip: false` 在该模式下也不是缺陷。

**解决方法：**

- 清理应用/DNS 缓存后，用同域名、同节点、同网络比较实际连接元数据中的域名、目标 IP 和规则。
- 若恢复域名不稳定，可在独立测试副本中切换 fake-ip 做 A/B；不要默认 fake-ip 会替代所有 DNS，也不要假定所有协议都由远端节点解析。
- 对必须使用 redir-host 的应用保留兼容路径，并只为实测失败的域名/协议调整嗅探或解析策略。

### 4. DNS policy 优先级和默认 fallback 不应混为一谈

**优先级：P2；性质：默认行为和覆盖范围的可维护性风险。**

**位置：150-167 行。**

官方文档规定 `nameserver-policy` 优先于 `nameserver` 和 `fallback`。命中境外 policy 的域名直接使用指定解析路径；未命中的域名才需要重点核对普通 nameserver/fallback 行为。`fallback-lazy-query: true` 是先检查主解析结果是否符合过滤条件再决定查询 fallback，不是“只在主 DNS 超时才查询”。默认过滤也不能识别全部错误答案。

`direct-nameserver-follow-policy: false` 会让直连域名使用专门的国内解析器而不跟随 policy，这是明确配置的取舍，只有与实际直连需求冲突时才是问题。geosite 数据加载失败也不能未经日志验证就断言必然静默回退；可能出现加载错误或启动失败。

**解决方法：**

- 按目标核心默认值评估是否需要显式 `fallback-filter`，记录选择依据；不要把省略字段当作确定性缺陷。
- 对不在 geosite 集合中的外站域名检查解析路径；必要时为实测问题域名设置明确 policy。
- 检查 Geo 数据加载日志、policy 查询超时和直连专用 DNS 的实际答案。
- 若需让直连域名也遵守 policy，再评估启用 `direct-nameserver-follow-policy`，并验证不会引入代理依赖。

## 三、可用性与兼容性

### 5. 排除正则点号未转义

**优先级：P2；性质：确定的正则语义偏差，误伤程度取决于节点名。**

**位置：26、46、66 行。**

`0.1`、`0.5` 中的 `.` 匹配任意字符，可能错误排除包含 `0x1`、`0-5` 等片段的合法节点。`5x`、`x8`、`x3` 本身没有点号，不属于这一错误。

**解决方法：** 在 YAML 双引号字符串中用 `0\\.1`、`0\\.5` 表示字面点号；如名称明确是倍率，再添加倍率边界或标记。使用真实脱敏节点名比较修改前后排除清单，避免改变原有倍率排除意图。

### 6. 节点筛选可能过宽，不能只检查是否编译成功

**优先级：P2；性质：候选集合风险，不是负向前瞻语法错误。**

**位置：173-174、178、181、194-195、199-200 行。**

`no_jp` 包含单字 `日` 和 `家宽` 等关键词，`no_hktw` 包含单字 `港` 等词，大小写不敏感的 `JP`、`HK`、`TW` 也可能匹配不代表地区的片段。宽筛选可能误排除可用节点；反之，非港台筛选未覆盖所有含单字 `台` 或 `臺` 的节点名，是否漏掉台湾节点取决于实际命名。

**解决方法：** 保留两个 YAML 锚点以集中维护，在真实节点名样本上列出保留/排除结果，补齐实际出现的地区写法并确认单字兜底的业务意图。目标核心 `-t` 通过不代表各组候选正确，还必须查看 API/面板候选及当前节点。

### 7. 单一探测目标和频繁全量探测

**优先级：P2；性质：线路代表性和手机资源消耗风险。**

**位置：16-23、36-43、56-63、189-200 行。**

gstatic 检查通过节点执行；某线路能访问目标服务却不能访问 gstatic 时，健康状态可能不代表实际业务。120 秒、`lazy: false` 会在机场未被使用时仍检查全量节点，对节点数较多的 Android 设备带来连接、流量和电量开销。`max-failed-times: 1` 可增加失败后检查敏感度，但并不表示一次失败立即换节点，更不必然中断既有连接。

**解决方法：** 对比节点探测和真实业务可达性，必要时选更具代表性的探测地址并校验状态码；根据移动网络、节点数量调节 timeout、interval、lazy 和失败检查阈值。更改 lazy 需考虑切到久未使用机场时状态过期的问题。

### 8. Android 平台和额外监听端口

**优先级：P2；性质：平台/客户端覆盖风险，不是同时配置端口就必然冲突。**

**位置：71-75、125-136 行。**

官方文档指出 `auto-redirect` 依赖 Linux 重定向机制，在 Android 场景有仅本地 IPv4 等限制；不能把它当成所有流量的通用开关。多个代理监听端口可以与 TUN 共存，但 FlClash 是否采用、覆盖或忽略这些字段，应看有效运行配置及日志。端口被其他进程占用时也可能造成启动错误。

**解决方法：** 在 Android 测试副本中保留 VPN/TUN 所需字段，停用确实不使用的端口；仅在日志或对照测试支持时调整 `auto-redirect`。分别验证 TCP/UDP、IPv4/IPv6、应用排除和热点共享，不因一个网页可访问就认定接管完整。

### 9. 缺少显式私网 IP 直连兜底

**优先级：P2；性质：文件内缺少显式规则已确认，故障依赖实际路由和外部清单。**

**位置：205-246 行；225 行只有 private_domain。**

私网域名规则不能替代私网 IP 规则。本轮未读取自建规则集，所以不能断言里面绝无私网 IP 例外；但该 YAML 的可见规则没有统一的私网网段直连兜底。被 TUN 捕获、且未命中前序例外的局域网 IP，可能落入 MATCH 后走代理。回环和链路本地是否进入 TUN还取决于平台路由，不能一概而论。

**解决方法：** 按业务在规则前部添加 `10/8`、`172.16/12`、`192.168/16` 等私网 `DIRECT,no-resolve` 规则，并按需要处理回环、链路本地和 IPv6 网段。若有公司内网代理需求应保留其更优先的例外。实测路由器、打印机、手机连接配对；IP 直连规则不能替代发现协议/多播支持。

### 10. IPv6 关闭的适用范围

**优先级：P2/P3；性质：网络环境约束。**

**位置：76、141 行。**

双重 `ipv6: false` 会限制 AAAA/IPv6 使用，对 IPv6-only 服务不兼容。Android NAT64/464XLAT 是否失败取决于系统转换、VPN、节点地址族和核心实现，不能仅据此断言所有 IPv6-only 移动网络都不可用，也不是错误 IPv4 答案的直接证据。

**解决方法：** 如实际网络/服务需要 IPv6，在测试副本中开启并补齐对应路由、私网规则和节点能力检查；若保留 IPv4-only，写明约束并做移动网络对照测试。

### 11. 嗅探范围及目的地址改写

**优先级：P2/P3；性质：条件性协议兼容风险。**

**位置：101-122 行，重点 107-108 行。**

HTTP 端口范围较宽且允许 override。端口范围本身不会把所有非 HTTP 流量当作 HTTP；内核仍会识别协议。但在错误 Host、共享 IP、应用自定义协议等情况下，目的地址改写可能不符合应用意图。skip-domain 又会使部分 Apple/小米相关连接不经过相同嗅探路径。

**解决方法：** 对实测失败的连接检查嗅探前后的域名/目的 IP；缩小端口或关闭 override 做对照，并为必要服务补明确规则。不要把 TLS/QUIC 嗅探开启本身认定为错误。

## 四、策略语义与维护

### 12. 原始节点直选与 fallback 共存

**优先级：P2/P3；性质：业务选择，非必然 bug。**

**位置：177-185 行。**

`include-all: true` 和流媒体组 `use: [cheap]` 会提供原始节点候选，用户直选节点时不再经过同一机场 fallback。这可以是有意保留的控制权；但若用户以为所有候选都自动兜底，就会误解故障转移和出口 IP。`store-selected: true` 也会保存选择，文件第一项不等于每次启动实际选中项。

**解决方法：** 核对各组实际保存的选择，区分“选机场 fallback”和“选单节点”。只有确认不需要直选时才收敛候选；保留每个用途选择机场的能力，跨机场自动档作为额外选项，不擅自改成只有一个自动组。

### 13. 服务映射与规则优先级

**优先级：P3；性质：需要业务确认。**

**位置：219、221、231、234、236 行等。**

media 指向漫画动漫、Google 指向 AI、Telegram 指向流媒体、TikTok 指向节点选择，不一定是错误，不能仅因名字不同改规则。另有 `proxylite -> DIRECT` 位于通用外站代理规则之前；本轮未读取它的内容，不能声称其中包含任何特定外站，但若问题域名命中它，就会优先直连。直连自建例外也有类似优先级。

**解决方法：** 用问题域名的真实 rule 命中记录定位，不按猜测重排规则；如确需改变，只增加或修正明确的业务例外并记录依据。

### 14. 外部数据可达性、版本与缓存

**优先级：P2/P3；性质：启动与更新可靠性风险。**

**位置：80-87、254-375 行。**

Geo 数据和规则均依赖 jsDelivr，规则引用 `@main`/`@meta`、Geo 引用 `@release`，内容可随分支更新。省略 rule-provider path 不代表没有缓存；但首次加载无缓存、缓存损坏、CDN 失败、格式与核心版本不兼容时可能启动失败或更新失败。不能未经日志证明就宣称所有下载都必然 DIRECT、失败后必然静默落到 MATCH。`@meta` 是上游正式使用的发布分支，名称本身不是非法格式。

**解决方法：** 检查启动/更新日志、条目数量和持久化缓存；关键场景预置已验证文件，建立更新失败时保留旧数据的验证流程。可对已验证版本固定 commit，但要同时安排更新机制，避免永远冻结规则。不要通过删除规则来掩盖下载失败。

## 五、安全暴露面

### 15. DNS 绑定所有 IPv4 接口

**优先级：P2；性质：绑定值已确认，实际外部可达依赖防火墙/Android。**

**位置：77、140 行。**

`allow-lan: false` 不会把独立 `dns.listen: 0.0.0.0:1053` 改为回环绑定。若网络可达，其他设备可能使用此 DNS。配置本身不意味着暴露到公网，也不意味着已经发生 DNS 劫持。

**解决方法：** 不提供 LAN DNS 时用回环监听或客户端支持的受控方式；提供 LAN DNS 时限制来源、监听接口和防火墙范围。确认 FlClash 不会覆盖该值，并从同网段设备验证实际可达性。

### 16. 回环控制接口无认证

**优先级：P2/P3；性质：本机威胁模型相关。**

**位置：90-91 行。**

`127.0.0.1:9090` 已阻止直接的 LAN API 暴露，但空 secret 允许能访问该回环端口的本机进程操作 API。Android 其他应用是否可以访问、FlClash 是否重写端口和 secret，需核对实际客户端行为。

**解决方法：** 有效运行配置中启用强认证并保持回环绑定；先确认 FlClash 面板/API 集成方式，避免设置 secret 后客户端控制失效。不要把实际 secret 提交到公开仓库。

## 六、执行与验证顺序

1. 记录 FlClash 版本、核心版本、运行模式、有效配置、当前保存的组选择及一条失败域名的日志。
2. 区分目标 IP 与公网出口 IP；至少用两个独立解析器交叉核对答案，并记录真实连接失败原因。
3. 验证境外 DoH 的出站链、节点域名解析、UDP/TCP 53 劫持与应用加密 DNS 的行为。
4. 检查所有相关 Geo/规则加载状态、候选节点和 MATCH/DIRECT 命中；不能只检查 `-t`。
5. 在独立测试副本中每次只改变一个因素：fake-ip、私人 DNS、指定可用节点、嗅探 override 或平台字段，避免多项改动掩盖根因。
6. 修正字面点号，并对节点筛选做保留/排除样本验证；保留 YAML 锚点和用途/机场选择结构。
7. 按需补私网规则、调整探测资源、收敛监听和认证；验证 LAN、UDP、移动网络及重启后的保存选择。

本报告提供修复建议，不代表已经应用或实机验证。当前没有证据把任何单一参数认定为“所有外站 IP 都错误”的唯一根因。
